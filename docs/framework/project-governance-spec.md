# 项目治理规范 (Project Governance Specification)

> **定义"要做到什么"** - 项目级别的治理规则

---

## 适用条件

本规范适用于以下场景：

1. **使用 RDD (Roadmap Driven Development) 开发范式的项目**
2. **由 Agent 驱动的开发过程**
3. **需要多阶段交付的软件项目**
4. **需要人工审核关键决策的项目**

### 强制适用

- 所有采用 RDD 框架的项目必须遵守本规范
- 所有 Agent 执行的开发任务必须遵守本规范

### 可选适用

- 纯人工开发项目可参考本规范
- 单阶段小型项目可简化适用

---

## 目标与验收标准

### 目标

1. **确保项目方向正确**：Roadmap 由人类主导，Agent 沿轨道执行
2. **保证交付质量**：每个 Stage 可验收、可回滚、可 handoff
3. **防止知识腐化**：技术债可见，不以隐性知识管理
4. **支持协作与恢复**：新 Agent 可凭文档自举，支持中断恢复

### 验收标准

| 编号 | 标准 | 验证方式 |
|------|------|----------|
| V1 | 所有 Stage 有清晰的设计文档 | 文档存在且内容完整 |
| V2 | 所有技术债在台账中显式记录 | 台账条目与实际一致 |
| V3 | 所有 ADR 记录"对后续 Stage 影响" | ADR 字段非空 |
| V4 | fresh-agent-check 通过 | 新 Agent 可独立接手 |
| V5 | 无"文档待补"状态 | 文档与实现同步完成 |

### fresh-agent-check 定义

**fresh-agent-check** 是一种验证机制，用于确保项目文档的完整性和可恢复性。该检查验证一个新的 Agent（无历史上下文）是否能够仅凭项目文档理解当前项目状态并继续工作。

**检查内容**：
- 读取并理解当前 Stage 文档
- 理解项目架构和技术栈
- 了解已知技术债和决策背景
- 能够复现测试和验证流程

**通过标准**：
- 新 Agent 可独立理解项目状态
- 新 Agent 可执行已完成的测试
- 新 Agent 可继续未完成的任务

## 禁止行为清单（9 条）

以下行为在任何情况下都**严格禁止**：

### 1. 无设计文档开始实现

```
禁止：在完成设计文档之前开始编码实现
必须：先完成设计文档，再开始编码
```

**原因**：设计文档是 Stage 的契约，缺失会导致方向偏离和返工。

### 2. Scope 悄悄扩大

```
禁止：在实现过程中未经审核扩大 Stage 范围
必须：发现 scope 变化时立即停下，先更新文档，等待审核
```

**原因**：Scope 蔓延是项目延期的主要原因，必须显式管理。

### 3. "文档待补"状态声称完成

```
禁止：以"文档待补"状态声称 Stage 完成
必须：文档必须与实现同步完成，不允许后续补
```

**原因**：事后补文档往往遗漏细节，导致知识断层。

### 4. 多个 Stage 核心未知数放同一 Stage

```
禁止：在一个 Stage 中验证多个核心未知数
必须：每个 Stage 只验证一小组清晰假设
```

**原因**：多未知数叠加会导致失败原因难以定位。

### 5. 依赖"口口相传"来运行测试

```
禁止：测试依赖口头传达的特殊步骤或环境
必须：测试必须可通过 Task 入口复现
```

**原因**：隐性知识无法传递给新 Agent。

### 6. 编写隐藏平台假设的脚本

```
禁止：脚本中隐藏对平台/环境的假设
必须：环境假设必须显式文档化
```

**原因**：隐藏假设导致跨环境失败。

### 7. 在理解运行时约束之前引入宽泛接口

```
禁止：在未验证运行时约束前设计通用接口
必须：先验证约束，再设计接口
```

**原因**：过早抽象导致接口与实际需求不匹配。

### 8. 过早把昂贵检查塞进默认编辑循环

```
禁止：将耗时长的检查作为默认行为
必须：昂贵检查应该显式触发，不是默认行为
```

**原因**：影响开发效率，导致开发者绕过检查。

### 9. 将技术债当作隐性知识管理

```
禁止：技术债只在代码注释或口头讨论中存在
必须：所有已知缺口必须在台账中显式记录
```

**原因**：隐性技术债会持续积累，最终导致系统腐化。

## 质量门禁

> **注意**：Gate 0（Stage 启动检查）定义在 `agentic-code-execution-spec.md` 中，用于在 Stage 启动时检查前置条件和上下文加载。本规范定义的 Gate 1-5 覆盖 Stage 推进过程中的质量检查。

### Gate 1：设计文档前置检查

**阻塞行为**：禁止实现

**检查项**：
- [ ] 设计文档是否完成
- [ ] 目标是否清晰
- [ ] 非目标是否显式声明
- [ ] 验收标准是否可测试
- [ ] 回滚方案是否存在

### Gate 2：方案 Review（写代码前）

**阻塞行为**：禁止编码

**检查项**：
- [ ] 多模型 Review 是否触发
- [ ] AI 初筛是否完成
- [ ] 高置信度 findings 是否修复

### Gate 3：实现与测试

**阻塞行为**：禁止提交

**检查项**：
- [ ] E2E 测试是否通过
- [ ] 单元测试覆盖率是否 >= 20%
- [ ] 至少 2 条高信号 E2E 路径
- [ ] 真实环境验证是否通过（非 mock）
- [ ] 干净环境二级验证是否通过

### Gate 4：代码 Review（E2E 通过后）

**阻塞行为**：禁止完成

**检查项**：
- [ ] 所有阻塞性 findings 是否修复
- [ ] 所有验收标准是否达成

### Gate 5：完成门禁检查

**阻塞行为**：禁止进入下一 Stage

**检查项**：
- [ ] 主要假设被验证或证伪
- [ ] 测试可通过 Task 入口复现
- [ ] 无未文档化的手工步骤
- [ ] 实现与设计一致（差异已记录）
- [ ] 新能力有 CLI 子命令
- [ ] 技术债台账已更新
- [ ] ADR 已记录（"对后续 Stage 影响"不可留空）
- [ ] fresh-agent-check 通过

## 文档更新义务

Stage 完成时**必须同步更新**以下文档：

### 必须更新的文档列表

| 文档 | 更新内容 | 更新时机 |
|------|----------|----------|
| `docs/stages/stage-N.md` | 实现差异、验收标准变化 | Stage 完成时 |
| `docs/stages/stage-N-review-log.md` | findings、采纳/不采纳理由 | Review 完成时 |
| `docs/08-autonomous-decisions.md` | ADR、假设偏差 | 决策发生时 |
| `docs/12-technical-debt.md` | 新增/偿还技术债 | Stage 完成时 |
| `docs/11-next-steps.md` | 进度、下一步入场条件 | Stage 完成时 |
| `CHANGELOG.md` | 本 Stage 变更摘要 | Stage 完成时 |

### 防止文档腐化的三规则

1. **即时更新**：发现设计偏差立即更新，不等 Stage 结束
2. **实质内容**：必须有具体内容，不能只写"待定"
3. **版本刷新**：所有"当前状态"字段同步刷新

## Must/Should/May 规则

### Must（必须）

以下规则**必须**遵守，违反将阻塞 Stage 推进：

- Must: 每次变更前更新 Roadmap
- Must: Stage 启动前完成设计文档
- Must: 文档与实现同步完成
- Must: 所有技术债记入台账
- Must: ADR 记录"对后续 Stage 影响"
- Must: fresh-agent-check 通过才能完成 Stage

### Should（应该）

以下规则**应该**遵守，特殊情况可例外但需说明：

- Should: 每个 Stage 时长控制在 1-3 天
- Should: 技术债"降级功能+架构级"积压超过 3 条时安排专项迭代
- Should: 连续失败 3 次触发人工介入
- Should: 多模型分歧严重时暂停并通知

### May（可以）

以下规则是建议，可根据情况灵活处理：

- May: 使用 Stage retrospective 进行复盘
- May: 在 ADR 中记录备选方案
- May: 对高风险 Stage 进行额外的 Review 轮次

## Good/Bad Case 示例

### Good Case：Scope 发现变化时的正确处理

```
场景：实现 Stage 3 时发现需要新增一个依赖项

正确做法：
1. 立即停止编码
2. 更新 stage-3.md 的"已知限制"章节
3. 在技术债台账中记录新增依赖的影响
4. 提交设计文档变更，等待审核
5. 审核通过后继续实现
```

### Bad Case：Scope 悄悄扩大

```
场景：实现 Stage 3 时发现需要新增一个依赖项

错误做法：
1. 直接添加依赖并继续实现
2. 实现"顺便"多加了一些相关功能
3. Stage 结束时才在文档中提及
4. 导致后续 Stage 假设失效
```

### Good Case：技术债的显式管理

```
场景：Stage 4 中为了赶进度采用了临时方案

正确做法：
1. 在 stage-4.md 的"已知限制"章节记录临时方案
2. 在 technical-debt.md 中创建技术债条目：
   - TD-001: 认证模块使用内存存储
   - 优先级: 降级功能/模块级
   - 来源: Stage 4 原型期主动妥协
   - 建议落地 Stage: Stage 6
3. 在 ADR 中记录决策原因和对后续影响
```

### Bad Case：技术债的隐性管理

```
场景：Stage 4 中为了赶进度采用了临时方案

错误做法：
1. 在代码注释中写 "// TODO: 后续要改"
2. 口头告诉团队成员"这个地方要改"
3. 没有任何文档记录
4. 一个月后没人记得这个问题
```

### Good Case：文档同步完成

```
场景：Stage 5 实现完成

正确做法：
1. 运行所有测试确保通过
2. 更新 stage-5.md 记录实现差异
3. 更新 technical-debt.md 记录新增技术债
4. 更新 next-steps.md 标记进度
5. 更新 CHANGELOG.md 记录变更
6. 运行 fresh-agent-check
7. 所有文档更新完成后，标记 Stage 完成
```

### Bad Case：文档待补

```
场景：Stage 5 实现完成

错误做法：
1. 运行测试通过
2. 标记 Stage 完成
3. 留下 comment "文档待补"
4. 开始下一个 Stage
5. 文档永远没有补上
```

## 边界声明

### 本规范覆盖范围

- 项目级别的治理规则
- Stage 级别的质量门禁
- 文档更新的义务和时机
- 禁止行为的定义

### 本规范不覆盖范围

- 具体的编码规范（应参考其他规范）
- 工具的具体使用方法（参考 agentic-code-execution-spec.md）
- Review 的具体流程（参考 agentic-code-execution-spec.md）
- Hook 通知的配置方法（参考相关配置文档）

### 与其他规范的关系

- 本规范定义"要做到什么"
- `agentic-code-execution-spec.md` 定义"怎么做"
- `standards-authoring-spec.md` 定义"如何写规范"

## 冲突优先级

当不同规范之间出现冲突时，按以下优先级处理：

### 优先级排序（从高到低）

1. **安全与合规要求**：涉及安全、隐私、合规的规则优先级最高
2. **本规范（项目治理规范）**：定义项目的核心治理规则
3. **agentic-code-execution-spec.md**：定义执行层面的规则
4. **项目特定规范**：项目自定义的补充规则
5. **通用最佳实践**：行业通用的最佳实践建议

### 冲突解决流程

```
1. 识别冲突涉及的规范
2. 按优先级确定适用规范
3. 在 ADR 中记录冲突和解决方式
4. 如优先级不明确，暂停并请求人工决策
```

## 生命周期

### 规范创建

1. 需求提出并讨论
2. 按照 standards-authoring-spec.md 编写
3. Review 并通过
4. 发布并生效

### 规范维护

| 触发条件 | 动作 |
|----------|------|
| 发现规范与实际不符 | 提出修订建议 |
| 项目模式变化 | 评估规范适用性 |
| 连续 3 次违反同一规则 | 评估规则合理性 |

### 规范废弃

1. 标记为"待废弃"
2. 提供替代方案或迁移路径
3. 过渡期结束后正式废弃
