# 规范编写规范 (Standards Authoring Specification)

> **定义"如何写规范"** - 规范文档的编写标准

---

## 适用条件

本规范适用于以下场景：

1. **创建新的规范文档**：当需要制定新的项目规范时
2. **修改现有规范**：当需要更新或修订现有规范时
3. **审核规范文档**：当需要评估规范质量时
4. **迁移规范文档**：当需要将规范迁移到新格式时

### 强制适用

- RDD 框架内的所有规范文档
- 项目级别的治理规范
- 执行层面的操作规范

### 可选适用

- 团队内部的临时规范
- 非正式的指导文档

---

## 规范必需要素

所有规范文档**必须**包含以下要素：

### 1. 适用条件 (强制)

**目的**：明确规范适用的范围和场景

**格式要求**：
```markdown
## 适用条件

本规范适用于以下场景：

1. **[场景1描述]**
2. **[场景2描述]**
...

### 强制适用

- [强制适用的具体场景]

### 可选适用

- [可选适用的具体场景]
```

**示例**：
```markdown
## 适用条件

本规范适用于以下场景：

1. **使用 RDD 开发范式的项目**
2. **由 Agent 驱动的开发过程**

### 强制适用

- 所有采用 RDD 框架的项目必须遵守本规范

### 可选适用

- 纯人工开发项目可参考本规范
```

### 2. Good/Bad Case (强制)

**目的**：通过对比说明规范的正确实践

**格式要求**：
```markdown
## Good/Bad Case 示例

### Good Case：[场景描述]

```
[正确做法的代码或步骤]
```

**说明**：[为什么这样做是正确的]

### Bad Case：[场景描述]

```
[错误做法的代码或步骤]
```

**说明**：[为什么这样做是错误的，以及后果]
```

**要求**：
- 每个 Good Case 必须有对应的 Bad Case
- 至少包含 3 组 Good/Bad Case 示例
- 示例必须具体、可操作
- 必须说明正确/错误的原因

### 3. 边界声明 (强制)

**目的**：明确规范的边界，避免范围蔓延

**格式要求**：
```markdown
## 边界声明

### 本规范覆盖范围

- [覆盖的内容1]
- [覆盖的内容2]

### 本规范不覆盖范围

- [不覆盖的内容1]
- [不覆盖的内容2]

### 与其他规范的关系

- 本规范与 [其他规范] 的关系说明
```

**示例**：
```markdown
## 边界声明

### 本规范覆盖范围

- 项目级别的治理规则
- Stage 级别的质量门禁

### 本规范不覆盖范围

- 具体的编码规范
- 工具的具体使用方法

### 与其他规范的关系

- 本规范定义"要做到什么"
- `agentic-code-execution-spec.md` 定义"怎么做"
```

### 4. 冲突优先级 (强制)

**目的**：当多个规范冲突时，提供明确的解决路径

**格式要求**：
```markdown
## 冲突优先级

当不同规范之间出现冲突时，按以下优先级处理：

### 优先级排序（从高到低）

1. **[最高优先级]**：说明
2. **[次高优先级]**：说明
...

### 冲突解决流程

```
1. [步骤1]
2. [步骤2]
...
```
```

**示例**：
```markdown
## 冲突优先级

### 优先级排序（从高到低）

1. **安全与合规要求**：涉及安全、隐私、合规的规则优先级最高
2. **本规范（项目治理规范）**：定义项目的核心治理规则
3. **agentic-code-execution-spec.md**：定义执行层面的规则

### 冲突解决流程

```
1. 识别冲突涉及的规范
2. 按优先级确定适用规范
3. 在 ADR 中记录冲突和解决方式
```
```

### 5. 生命周期 (强制)

**目的**：规范本身也需要生命周期管理

**格式要求**：
```markdown
## 生命周期

### 规范创建

1. [创建步骤1]
2. [创建步骤2]
...

### 规范维护

| 触发条件 | 动作 |
|----------|------|
| [条件1] | [动作1] |
| [条件2] | [动作2] |

### 规范废弃

1. [废弃步骤1]
2. [废弃步骤2]
...

### 版本历史

| 版本 | 日期 | 变更说明 |
|------|------|----------|
| 1.0.0 | YYYY-MM-DD | 初始版本 |
```

## 格式规范

### 文档结构

规范文档应按以下结构组织：

```markdown
# [规范名称]

> **[一句话描述规范的目的]**

---

## 适用条件
[必需要素1]

## [核心内容章节1]
[规范的主要内容]

## [核心内容章节2]
[规范的主要内容]

...

## Good/Bad Case 示例
[必需要素2]

## 边界声明
[必需要素3]

## 冲突优先级
[必需要素4]

## 生命周期
[必需要素5]

---

*[页脚说明]*
```

### 标题层级

| 层级 | 用途 | 示例 |
|------|------|------|
| H1 | 文档标题 | `# 项目治理规范` |
| H2 | 主要章节 | `## 适用条件` |
| H3 | 子章节 | `### 强制适用` |
| H4 | 更细分章节 | `#### 示例` |

**要求**：
- 一个文档只有一个 H1 标题
- 层级不能跳过（如 H1 直接跳 H3）
- 标题应简洁明了

### 列表格式

#### 无序列表

```markdown
- 项目1
- 项目2
  - 子项目1
  - 子项目2
- 项目3
```

#### 有序列表

```markdown
1. 第一步
2. 第二步
3. 第三步
```

#### 任务列表

```markdown
- [ ] 未完成
- [x] 已完成
```

### 表格格式

```markdown
| 列1 | 列2 | 列3 |
|------|------|------|
| 内容1 | 内容2 | 内容3 |
| 内容4 | 内容5 | 内容6 |
```

**要求**：
- 表头必须清晰
- 列宽应对齐
- 复杂表格考虑拆分

### 代码块格式

#### 行内代码

```markdown
使用 `code` 表示行内代码
```

#### 代码块

````markdown
```[语言]
代码内容
```
````

#### 命令示例

````markdown
```bash
command --option value
```
````

### 强调格式

| 格式 | 语法 | 用途 |
|------|------|------|
| 粗体 | `**文本**` | 重要概念、关键术语 |
| 斜体 | `*文本*` | 引用、说明 |
| 粗斜体 | `***文本***` | 极其重要 |

### 引用格式

```markdown
> 引用内容
> 可以多行
```

### 分隔线

```markdown
---

使用三个或更多的连字符
```

## 审阅流程

### 规范创建流程

```
规范创建流程
│
├── 1. 需求提出
│   ├── 明确规范目的
│   ├── 确定适用范围
│   └── 收集参考资料
│
├── 2. 草案编写
│   ├── 按照模板编写
│   ├── 包含所有必需要素
│   └── 添加 Good/Bad Case
│
├── 3. 内部审阅
│   ├── 格式检查
│   ├── 内容完整性检查
│   └── 可执行性检查
│
├── 4. 试运行
│   ├── 在实际项目中应用
│   ├── 收集反馈
│   └── 记录问题
│
├── 5. 修订完善
│   ├── 根据反馈修订
│   ├── 补充示例
│   └── 完善边界声明
│
└── 6. 正式发布
    ├── 确定版本号
    ├── 记录发布日期
    └── 通知相关人员
```

### 审阅检查清单

```yaml
审阅检查清单:
  必需要素:
    - [ ] 适用条件是否明确
    - [ ] Good/Bad Case 是否完整（至少3组）
    - [ ] 边界声明是否清晰
    - [ ] 冲突优先级是否明确
    - [ ] 生命周期是否定义

  格式规范:
    - [ ] 标题层级是否正确
    - [ ] 列表格式是否一致
    - [ ] 表格是否对齐
    - [ ] 代码块是否标注语言

  内容质量:
    - [ ] 内容是否清晰易懂
    - [ ] 示例是否具体可操作
    - [ ] 是否有歧义
    - [ ] 是否可执行

  一致性:
    - [ ] 与其他规范是否一致
    - [ ] 术语使用是否一致
    - [ ] 格式风格是否一致
```

### 审阅意见格式

```markdown
## 审阅意见

### 总体评价
[通过/需修改/不通过]

### 具体意见

#### 章节：[章节名称]
- **严重程度**: [阻塞/警告/建议]
- **描述**: [具体问题描述]
- **建议**: [修改建议]

### 必须修改项
1. [必须修改项1]
2. [必须修改项2]

### 建议修改项
1. [建议修改项1]
2. [建议修改项2]
```

## 维护指南

### 规范更新触发条件

| 触发条件 | 更新类型 | 处理方式 |
|----------|----------|----------|
| 发现规范与实际不符 | 修正 | 提出修订，快速更新 |
| 项目模式变化 | 扩展 | 评估影响，谨慎更新 |
| 连续 3 次违反同一规则 | 评估 | 评估规则合理性，可能废弃 |
| 新技术或新实践引入 | 扩展 | 讨论后新增相关章节 |
| 安全或合规要求变化 | 紧急 | 立即更新 |

### 版本号规则

采用语义化版本号：`主版本.次版本.修订版本`

| 版本类型 | 变更说明 | 示例 |
|----------|----------|------|
| 主版本 | 不兼容的重大变更 | 1.0.0 → 2.0.0 |
| 次版本 | 向后兼容的功能新增 | 1.0.0 → 1.1.0 |
| 修订版本 | 向后兼容的问题修正 | 1.0.0 → 1.0.1 |

### 变更记录

每次变更必须记录：

```markdown
## 版本历史

| 版本 | 日期 | 变更说明 | 作者 |
|------|------|----------|------|
| 1.1.0 | 2026-03-10 | 新增 xxx 章节 | [作者] |
| 1.0.1 | 2026-03-08 | 修复 xxx 描述不准确 | [作者] |
| 1.0.0 | 2026-03-06 | 初始版本 | [作者] |
```

### 废弃流程

```
规范废弃流程
│
├── 1. 识别废弃需求
│   ├── 规范已不适用
│   ├── 已有更好的替代
│   └── 使用频率极低
│
├── 2. 标记为"待废弃"
│   ├── 在规范顶部添加废弃警告
│   ├── 指明替代方案
│   └── 设定废弃日期
│
├── 3. 过渡期
│   ├── 保留规范但标记废弃
│   ├── 提供迁移指南
│   └── 监控使用情况
│
└── 4. 正式废弃
    ├── 从文档中移除或归档
    ├── 更新相关索引
    └── 通知所有使用者
```

### 废弃警告格式

```markdown
> **⚠️ 已废弃**
>
> 本规范已于 YYYY-MM-DD 标记为废弃，将于 YYYY-MM-DD 正式移除。
>
> **替代方案**: [替代规范名称]([链接])
>
> **迁移指南**: [迁移指南链接]
```

## Good/Bad Case 示例

### Good Case：完整的审查意见

```
## 审查意见

### 代码质量
- **严重程度**: 警告
- **位置**: src/auth/login.go:45
- **描述**: 密码比较使用了 == 而不是常量时间比较
- **建议**: 使用 crypto/subtle.ConstantTimeCompare

### 性能
- **严重程度**: 建议
- **位置**: src/db/query.go:120
- **描述**: 循环内执行数据库查询
- **建议**: 考虑批量查询

### 必须修改项
1. 修复密码比较问题
```

**说明**: 审查意见包含位置、描述、建议，分级清晰。

### Bad Case：模糊的审查意见

```
LGTM，但有几个小问题。
```

**说明**: 审查意见模糊，无法定位问题，缺乏具体建议。

## 边界声明

### 本规范覆盖范围

- 规范文档的必需要素
- 规范文档的格式标准
- 规范文档的审阅流程
- 规范文档的维护指南

### 本规范不覆盖范围

- 具体业务规范的编写（如代码规范、测试规范）
- 规范的技术实现（如规范检查工具）
- 规范的存储和分发机制

### 与其他规范的关系

- 本规范是元规范，定义如何编写规范
- `project-governance-spec.md` 和 `agentic-code-execution-spec.md` 是本规范的实例
- 本规范本身也必须遵守本规范的要求

## 冲突优先级

当不同规范编写要求之间出现冲突时，按以下优先级处理：

### 优先级排序（从高到低）

1. **内容完整性**：必需要素必须齐全，不能因格式而牺牲内容
2. **可执行性**：规范必须可执行，不能停留在抽象概念
3. **清晰易懂**：表达清晰，避免歧义
4. **格式一致**：格式与本文档要求一致

### 冲突解决流程

```
1. 识别冲突点
2. 评估各选项的优劣
3. 选择对读者最有利的方案
4. 在规范中说明选择理由
5. 记录为例外情况
```

## 生命周期

### 规范创建

1. **需求提出**
   - 明确规范目的和适用范围
   - 收集相关参考资料
   - 确定规范版本号

2. **草案编写**
   - 按照本文档模板编写
   - 包含所有必需要素
   - 至少 3 组 Good/Bad Case

3. **内部审阅**
   - 格式检查
   - 内容完整性检查
   - 可执行性检查

4. **试运行**
   - 在实际项目中应用
   - 收集反馈意见
   - 记录问题

5. **修订完善**
   - 根据反馈修订
   - 补充示例
   - 完善边界声明

6. **正式发布**
   - 确定版本号
   - 记录发布日期
   - 通知相关人员

### 规范维护

| 触发条件 | 动作 | 时间要求 |
|----------|------|----------|
| 发现规范与实际不符 | 提出修订建议 | 3 个工作日内处理 |
| 项目模式变化 | 评估规范适用性 | 1 周内完成评估 |
| 连续 3 次违反同一规则 | 评估规则合理性 | 2 周内完成评估 |
| 安全或合规要求变化 | 立即更新 | 立即处理 |

### 规范废弃

1. **识别废弃需求**
   - 规范已不适用于当前模式
   - 已有更好的替代方案
   - 使用频率极低

2. **标记为"待废弃"**
   - 在规范顶部添加废弃警告
   - 指明替代方案
   - 设定废弃日期（至少 1 个月过渡期）

3. **过渡期管理**
   - 保留规范但标记废弃
   - 提供迁移指南
   - 监控使用情况

4. **正式废弃**
   - 移动到归档目录
   - 更新相关索引
   - 通知所有使用者
